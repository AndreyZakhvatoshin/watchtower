## 2026-08-11 — Отдельный SSH-ключ на роль

Заведён `watchtower_ed25519` (Ed25519) вместо переиспользования личного
`id_ed25519`. Причина — область действия: компрометация машины требует отзыва
одного ключа на одном сервере, а не переразвешивания везде. Та же логика, что
у AD-26 про учётки с ограниченной областью.

Алиас на локальной машине — `~/.ssh/config`, хост `watchtower`,
с `IdentitiesOnly yes`: без него ssh перебирает все ключи агента подряд и может
упереться в лимит попыток аутентификации раньше, чем дойдёт до нужного.

**Пассфраза на ключе не установлена — принятый риск (решение от 2026-08-11).**
Приватный ключ лежит на диске в открытом виде: доступ к серверу получает любой,
кто прочитает файл — процесс под тем же пользователем, унесённый диск, попавший
в бэкап каталог `~/.ssh`.

Принято ради скорости ступени 0: ключ используется десятки раз в день вручную,
а `ssh-agent` на этой ступени ещё не настроен.

Пересмотреть, когда выполнится любое из: появится автоматический выкат по ssh
(ступень 1, Story 2.1), ключ понадобится на второй машине, ноутбук станет
выезжать за пределы дома. Лечится без перегенерации и без замены публичной
части: `ssh-keygen -p -f ~/.ssh/watchtower_ed25519`.

## 2026-08-11 — Парольный вход в SSH выключен файлом `00-hardening.conf`

Образ Selectel приезжает с включённым парольным входом и `PermitRootLogin yes`,
хотя в самом `/etc/ssh/sshd_config` стоит `PasswordAuthentication no`.

Причина расхождения: в начале `sshd_config` стоит
`Include /etc/ssh/sshd_config.d/*.conf`, а sshd применяет **первое** встреченное
значение, не последнее. Файл `50-cloud-init.conf` с `PasswordAuthentication yes`
подключается раньше строки `no` в основном файле и выигрывает.
Проверено: `sshd -T` показывал `passwordauthentication yes`.

Решение — `/etc/ssh/sshd_config.d/00-hardening.conf`, права 600:

```
PasswordAuthentication no
PermitRootLogin prohibit-password
KbdInteractiveAuthentication no
```

Имя начинается с `00-` намеренно: glob разворачивается по алфавиту, `00-` читается
раньше `50-`, и по правилу первого значения побеждает. Правка самого
`50-cloud-init.conf` не годится — cloud-init перегенерирует его при пересоздании
машины, и настройка тихо отвалится.

Проверка — `sshd -T`, а не чтение файлов: он печатает итоговый конфиг после всех
include. Порядок применения: `sshd -t` (синтаксис) → `sshd -T` (значения) →
`systemctl reload ssh` → вход из **нового** терминала при живой старой сессии.

## 2026-08-11 — PHP 8.5 из PPA `ondrej/php`

Ubuntu 24.04 несёт родной PHP 8.3, требуемой стеком 8.5 в репозиториях нет.
Источник — PPA `ondrej/php` (`deb.sury.org`), версия 8.5.9. Сторонний репозиторий
принят сознательно: альтернатива — понизить требование до 8.3.

Локальная машина и VDS обе на Ubuntu 24.04 noble, PHP берётся из одного и того же
PPA. Совпадение сред разработки и прода получено по факту; как критерий оно
закрывается только на ступени 2.

### Ловушка: `php` в PATH — не системный PHP

На локальной машине `php` резолвится в `~/.config/herd-lite/bin/php` (8.4.1),
который перехватывает вызов раньше системного. Composer, запущенный без явного
интерпретатора, разрешил бы зависимости под 8.4 и записал бы это в
`composer.lock`, разойдясь с продом.

Поэтому composer вызывается явно: `php8.5 <путь-к-composer.phar>`.

## 2026-08-11 — Полигон отработал: Let's Encrypt выпускает для `.ru`

**Исход: успех.** Сертификат для `mastetlab.ru` выпущен на **боевом** эндпоинте
Let's Encrypt (`https://acme-v02.api.letsencrypt.org/directory`), не на staging.
Отказа по признаку зоны нет.

Это эмпирический ответ на вопрос, которого нет в открытых источниках ни в одну
сторону: технический отказ Boulder выпускать для `.ru` первоисточником не
подтверждался, но и не опровергался. Теперь опровергнут — на 11.08.2026.

Параметры выпуска:

| | |
|---|---|
| Издатель | `C=US, O=Let's Encrypt, CN=YE1` |
| Субъект | `CN=mastetlab.ru`, SAN `DNS:mastetlab.ru` |
| Ключ | ECDSA P-256, подпись `ecdsa-with-SHA384` (умолчание acme.sh — `ec-256`) |
| Срок | 11.08.2026 12:34 UTC → 09.11.2026 12:34 UTC |
| Продление | по ARI, окно 09–11.10.2026, выбрано 10.10.2026 |

Цепочка отработала целиком и без ручных шагов: Keystone-аутентификация сервисного
пользователя → создание TXT `_acme-challenge.mastetlab.ru` через API DNS v2 →
проверка распространения → валидация УЦ → удаление TXT. Между добавлением записи
и успешной проверкой прошло 22 секунды — помог короткий negative TTL зоны (60 с
в SOA Selectel).

Роль `member` на проекте оказалась достаточной для управления записями; сужать
дальше не потребовалось.

### Что это меняет в спецификации

Формулировка `SPEC.md` (строка 81) — «требование автопродлеваемого TLS
невыполнимо» для `.ru` — **фактически неверна** и подлежит правке, как и AD-23.

Решение «зона вне `.ru`/`.su`» при этом **остаётся в силе**, но основание у него
теперь только одно, и оно не техническое: волатильность политики (соглашение
подписчика LE сменило редакцию v1.7 → v1.8 за 32 дня), один УЦ без запасного,
обязательная идентификация через ЕСИА с 01.09.2026, досудебное снятие
делегирования, непереносимость к иностранному регистратору (AD-26). Довод
«иначе TLS невыполним» из обоснования выбывает.

## 2026-08-11 — Полигон: `mastetlab.ru`, платный, 120 ₽

Полигонный домен для проверки цепочки ACME + DNS-01 + API DNS — `mastetlab.ru`,
регистрация в Selectel, 120 ₽.

**Акция «домен в подарок при аренде VDS» не сработала** — в панели цена полная.
Исследование от 06.08 давало её как «новым клиентам, промокод в течение 7 дней»,
но там же предупреждало на неё не рассчитывать. Выяснять условия через поддержку
не стали: выигрыш 120 ₽ против дней ожидания при дедлайне 31.08 (с 01.09 по
569-ФЗ регистрация `.ru` требует подтверждённой учётки Госуслуг).

Имя совпадает по второму уровню с боевым `mastetlab.com` — принято сознательно,
с оговоркой ниже.

**Полигон продом не становится ни при каком исходе**, даже при успешном выпуске
сертификата для `.ru`. Зона выбрана для прода по четырём причинам, к сертификатам
отношения не имеющим: один УЦ без запасного, идентификация через ЕСИА с 01.09.2026
с аннулированием непродлённых, досудебное снятие делегирования, непереносимость к
иностранному регистратору (конфликт с AD-26).

`mastetlab.ru` **не продлевается** и умирает вместе с полигоном. Риск принятого
имени — `.ru` и `.com` различаются одной буквой, перепутать в конфиге легко и
тихо. Отсюда правило: в конфигурации боевого хоста полигонная зона не появляется
вообще, а не «появляется закомментированной».

## 2026-08-11 — Отклонение: скелет собран локально, а не на сервере

История 1.1 (T4) предписывает `composer create-project` прямо в `/srv/watchtower`
на VDS. Сделано иначе: проект собран на локальной машине, залит в GitHub, на
сервер попадёт через `git clone`.

Почему так. Исходный порядок делает сервер источником кода: артефакт рождается
там, где его никто не версионирует, и репозиторий догоняет прод задним числом.
Обратный порядок с первого дня задаёт направление доставки «репозиторий → прод»,
которое всё равно закрепляется скриптом выката на ступени 1 (Story 2.1).

Что это стоит. Доставку пришлось решить раньше, чем её ставит история: на
ступени 0 это ручной `git clone` и `git pull` по ssh, без скрипта и без отката.
Осознанно временное решение, живёт до Story 2.1.

Расхождения сред это не создаёт: локальная машина и VDS обе на Ubuntu 24.04
noble с PHP 8.5 из одного PPA. `composer.lock` разрешён под 8.5 — см. запись про
ловушку herd-lite в PATH.

## 2026-08-11 — JSON-логи с первого коммита

Формат строки задан NFR8: `ts`, `level`, `module`, `correlation_id`, `msg`.
Штатный `Monolog\Formatter\JsonFormatter` даёт другой набор полей, поэтому свой —
`app/Logging/JsonFormatter.php` поверх `NormalizerFormatter`.

Подключение через **tap** (`app/Logging/UseJsonFormatter.php`), а не через ключ
`formatter` в конфиге канала: `formatter` учитывается только драйверами
`monolog` и `custom`, а формат нужен и каналу `daily` тоже.

Метка времени — ISO 8601 с микросекундами и смещением: сортируется
лексикографически и сохраняет порядок событий внутри одной секунды.

Остаточный контекст уезжает в `ctx`, чтобы верхний уровень строки оставался
стабильным по составу ключей — на это опирается чтение логов глазами до появления
Loki на ступени 3.

`correlation_id` проставляет `app/Http/Middleware/CorrelationId.php`, первым в
стеке (`prepend`), чтобы идентификатор попал и в записи более поздних middleware.
Входящий `X-Correlation-Id` принимается — на ступени 3 это склеит трассировку
PHP → Go-чекер по одному ключу, — но валидируется регуляркой и обрезается по
длине: значение уходит в лог и в заголовок ответа, то есть является недоверенным
вводом. Невалидный заменяется на свежий UUID.
